# Oracle Reply Surface

This document describes the current implementation shape of Oracle's reply surface.

For the canonical reply ownership contract, see
[reply-ownership.md](../contracts/reply-ownership.md).

## Canonical Reply Contract Surface

`POST /api/conversation/command` returns canonical `reply_text` generated by Oracle.

Satellites treat `reply_text` as the primary spoken reply surface and send it to `/api/speech/tts`.

This keeps capability logic server-side for future low-power satellites.

Satellites also reuse a stable `session_id` for short follow-up exchanges so Oracle can preserve conversational context.

Satellites claim durable alerts through authenticated
`POST /api/satellite/alerts/claim` and acknowledge the active lease after
delivery.

Oracle strips leading wake-word residue server-side before routing and silently ignores transcripts that normalize to empty text.

Playback-capable satellites expose authority-first playback state plus generic long-form control actions for audiobook transport.

## Follow-Up Conversations

Oracle supports short in-memory follow-up context keyed by `source + effective_session_id`.

Current behavior:

- Home Assistant follow-ups reuse Home Assistant `conversation_id`
- Ollama follow-ups include recent user and assistant turns
- the brain exposes `GET /api/conversation/session?source=...&session_id=...` for live
  session inspection
- satellites open a new session after a short inactivity timeout

Interaction state is intentionally process-local and expires as one bounded
session lifecycle; durable facts and operational records belong to Memory.
